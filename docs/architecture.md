# 아키텍처 — 경계를 어디에 그었나

파일을 어떻게 나눴는지보다 경계를 어디에 그었는지가 중요하다고 봤다.
이 저장소는 아래 네 가지 기준으로 경계를 나눴다.

## 기준 1 — 모델의 성격이 다른 곳

`plants/srb.py` 는 13-상태 단일 강체 방정식을 그대로 적분하고, 발 위치를
운동학적으로 고정한다. MPC 가 쓰는 모델과 같아서 모델 오차가 없다.

`plants/mujoco_plant.py` 는 접촉이 부드럽고, 발이 미끄러지고, 관절에 감쇠와
마찰이 있다. 모델 오차가 있다.

그래서 둘은 확인하는 게 다르다.

- SRB: MPC 가 자기 모델 위에서 제대로 동작하는지
- MuJoCo: 그 모델이 실제에 가까운 환경에서 얼마나 버티는지

한 클래스에 섞으면 실패했을 때 원인이 알고리즘인지 모델 차이인지 가리기 어렵다.
그래서 `plants/plant_base.py` 에 인터페이스를 두고 구현을 둘로 나눴다.
러너에서 바뀌는 건 한 줄이다.

```python
scenario_runner :  robot = SRBDynamics(...)
mujoco_runner   :  robot = MuJoCoPlant(...)
```

러너도 둘로 뒀다. 공유할 건 제어 로직이고, 실험을 돌리는 방식은 다르기 때문이다.
MuJoCo 쪽만 관절 토크·접촉력·yaw unwrap 진단값을 보고, 발산 판정도 다르다
(SRB 는 NaN, MuJoCo 는 `|roll|` 또는 `|pitch|` > 60°).

### 의도한 차이는 선언해 둔다

두 모델의 차이가 곧 실험 내용이라 차이를 없애지 않았다. 대신
`plants/model_audit.py` 에 의도한 차이 8 개를 선언하고, 선언에 없는 차이가
나오면 `UnexpectedModelMismatch` 를 던지게 했다. 그러면 모델이 모르는 사이에
바뀌는 걸 막을 수 있다.

| 의도한 차이 | 이유 |
|---|---|
| 마찰: MPC 사각뿔 / MuJoCo `cone="elliptic"` | MPC 제약이 실제 제약의 바깥 근사라는 걸 시험하려고 |
| 관절 감쇠·마찰·armature (MuJoCo 에만) | 이상적 모델이 무시한 것의 크기를 재려고 |
| 관성 텐서 (SRB 는 몸통만, MuJoCo 는 합성) | 논문 값을 그대로 쓰기로 해서 |

다리 순서, 힙 배치, μ, 토크 한계, 액추에이터 수, 발 반지름이 다르면 바로 실패한다.

## 기준 2 — 규약이 바뀌는 곳

단위, 좌표계, 부호, 원점, 각도 wrap 여부 같은 것들이다.

결함 13 개 중 6 개가 규약 문제였는데, 전부 독스트링에는 맞게 적혀 있었다.
독스트링만으로는 규약이 지켜지지 않아서, 경계에는 타입을 두기로 했다.

지금 타입으로 확인하는 것들:

- `RobotState`, `ControlCommand` 는 frozen 이고 생성할 때 형상을 검사한다.
- `ControlCommand` 는 스윙 다리의 힘이 정확히 0 인지 검사한다. 솔버 잔차 수준의 값도 거부한다.
- `MultiRateClock` 은 `sim_hz % mpc_hz != 0` 이면 생성 시점에 거부한다.
- `ScenarioSpec` 은 `TypedDict` 로 키와 타입을 선언했다 (아래).
- `Leg` 는 `IntEnum` 으로 FR/FL/RR/RL 순서를 고정한다.
- `_W` / `_B` 접미사로 프레임을 이름에 드러낸다.

### ScenarioSpec 을 TypedDict 로 둔 이유

시나리오는 러너에 넘기는 인자 묶음이고, `run_scenario(**spec)` 처럼 풀어서 넘긴다.
평범한 dict 로 두면 mypy 는 `dict[str, object]` 로만 보고 키 이름은 검사하지 않는다.

`TypedDict` 로 키와 타입을 선언해 뒀다. 그러면 `duration_s` 를 `duration` 으로
잘못 쓰거나 `horizon="10"` 처럼 타입을 틀린 걸 실행 전에 mypy(CI)에서 잡을 수 있다.

오타 난 키는 러너에 `**kwargs` 가 없어서 실행하면 `TypeError` 가 나긴 한다.
TypedDict 의 이점은 이걸 실행 전에, 테스트가 돌리지 않는 GALLERY 시나리오까지
잡아 준다는 것.

주의할 점 두 가지:

- 타입 주석을 붙인 곳에서만 검사된다. `scripts/run_sim.py` 의 `build_spec` 에
  `spec: ScenarioSpec = {...}` 라고 적어 둔 이유다. 빼면 그 자리에서만 검사가 빠진다.
- `total=False` 라서 키를 빠뜨린 건 잡지 못하고, 이 경우 러너 기본값이 쓰인다.
  시나리오마다 필요한 인자만 쓰려고 일부러 이렇게 뒀다.

## 기준 3 — 주기가 다른 곳

주기가 네 개 있다.

```
물리 적분 9000 Hz  ──▶  스윙·계획 1000 Hz  ──▶  MPC 30 Hz  ──▶  로깅 30~100 Hz
```

두 주기가 같으면 그 사이에서 생기는 문제가 로그에 안 보일 수 있다.
실제로 겪은 게 결함 10 이다.

### 결함 10 — 접촉이 바뀐 걸 MPC 가 늦게 반영함

접촉 상태(`is_stance_now`)는 보행 위상에서 계산한다
(`get_contact_state(phase, duty, offset)`). 센서로 감지한 값이 아니라
미리 정한 보행 스케줄이다.

위상은 매 스텝 갱신되는데 MPC 는 30 Hz 로만 풀었다. 그래서 스케줄상 다리가
바뀐 뒤에도 다음 MPC 틱까지 최대 33 ms 동안 이전 힘이 그대로 들어갔다.
공중에 뜬 다리에 힘이 실린 스텝이 1,800 개였다.

trot 반주기는 0.25 s 인데 MPC 간격(33.3 ms)으로 나누면 7.5 칸이라, 전이의
절반이 틱 사이에 떨어진다. 그래서 이륙 시각이 틱 사이에 오는 FR/RL 에서만 생겼다.

로그도 30 Hz 였는데, MPC 틱에 맞춰 찍히다 보니 늘 MPC 가 방금 풀린 직후
상태만 기록됐다. 그 사이 힘이 틀려 있던 구간은 로그에 남지 않았다.
그래서 진단 로그는 보려는 신호보다 빠르게, 다른 주기와 겹치지 않게 찍기로 했다.

### 고친 방법 — 고정 주기 + 접촉 전이 때 추가 풀이

고정 주기는 그대로 두고, 접촉 스케줄이 바뀌는 순간에 한 번 더 풀게 했다
(`experiments/mujoco_runner.py`).

```python
if clock.is_mpc_tick(sim_cnt) or contact_changed:
    fmpc, _ = mpc.solve(...)
```

풀이 횟수는 정규 90 회에 6 회가 늘었고(+6.7 %), 공중 다리에 힘이 실리던
1,800 스텝은 0 이 됐다.

### 실시간 관점에서 남은 문제

시뮬레이션은 계산이 끝나야 시간이 흐르니 데드라인이 없다. 그래서 +6.7 % 는
풀이 횟수가 늘었다는 뜻이지 실시간을 지켰다는 뜻은 아니다. 실제 하드웨어에서는
한 주기에 정규 풀이와 추가 풀이가 겹칠 수 있어서, 최악 실행시간(WCET)을 2 회
기준으로 잡아야 하고 풀이 시점도 불규칙해진다.

MIT Cheetah-Software(`ConvexMPCLocomotion`)는 다르게 처리한다. MPC 는
`iterationCounter % iterationsBetweenMPC == 0` 일 때만 풀고, 대신 보행 스케줄을
MPC 칸 수(정수)로 정의한다.

```cpp
trotting(horizonLength, Vec4<int>(0,5,5,0), Vec4<int>(5,5,5,5), "Trotting")
```

그러면 접촉 전이가 항상 MPC 틱 위에서만 일어나서 이 문제가 생기지 않는다.

| | MIT: 보행을 MPC 격자에 맞춤 | 이 저장소: 전이 때 추가 풀이 |
|---|---|---|
| 실시간성 | 주기당 1 회로 일정 | 최악 2 회, 시점 불규칙 |
| 대가 | 보행 타이밍이 MPC 간격의 정수배로 제한됨 | 보행 주기를 자유롭게 정할 수 있음 |

하드웨어로 옮긴다면 MIT 처럼 보행을 격자에 맞추거나, 추가 풀이를 유지하되
WCET 예산에 넣고 빈도를 제한하는 방법이 있다. 어느 쪽이 맞는지는 풀이 시간을
재 봐야 알 수 있다(로드맵 Step 7, 아직 안 함). 30 Hz 도 논문 값을 가져온 것이고
이 환경에서 재서 정한 값은 아니다.

### MPC 주기를 올리면?

계산량 말고도 고려할 게 있다.

- 예측 구간(`k × dt`)이 짧아진다. `k` 를 그대로 두고 `dt` 만 줄이면 MPC 가 다음
  접촉 전이를 못 보게 될 수 있다. 막으려면 `k` 를 늘려야 하고, 그러면 QP 가 커진다.
- 가중치 `L`, `K` 는 스텝당 비용이라 `dt` 가 바뀌면 의미가 달라진다.
  정상상태 속도 오차(`L_w_v` / `K_w_f` 균형)부터 다시 튜닝해야 한다.
- 반대로 오일러 이산화 오차는 `dt` 에 비례하니 오히려 줄어든다.

### 연속량은 계단으로 주지 않는다 (결함 13)

발판 목표를 MPC 주기로 갱신했더니 스윙 중인 발에 계단 입력이 들어갔다(19.7 mm).
발판 계획을 1 kHz 로 돌려서 고쳤다. 그러면 스윙 토크가 튀는 걸 막을 수 있다
(273.8 → 92.9 N·m).

## 기준 4 — 바뀌는 이유가 다른 곳

```
core  ◀──  control  ◀──  plants  ◀──  experiments  ◀──  viz
```

- `core/` 는 로봇이 바뀌어도 그대로다(회전, 각도 unwrap, 시계, 베지에, 기구학).
- `control/` 은 제어기가 바뀔 때 바뀐다.
- `plants/` 는 물리 모델이 바뀔 때 바뀐다.
- `viz/` 에는 아무것도 의존하지 않는다.

`core` 는 `control` 을 모르고, `control` 은 `plants` 를 모른다. 조립은 러너가 한다.

예전엔 이 방향이 깨져 있었다. `control/gait_planning.py` 에 matplotlib 을 쓰는
시각화 함수와 `__main__` 데모가 같이 있어서, 제어기만 import 해도 matplotlib 이
따라왔다. 그림 코드를 `viz/gait_plot.py` 로 옮겨서 고쳤다.

확인은 아래 명령으로 한다. 결과가 비어 있으면 된다.

```
grep -rn matplotlib src/quadruped_mpc/{core,control,plants,experiments}
```

## 저장소 경로는 paths.py 한 곳에서만

예전엔 스크립트마다 `ROOT = Path(__file__).resolve().parent.parent` 를 따로
계산해서, 파일을 옮기면 엉뚱한 경로를 가리켰다. `paths.py` 한 곳에서만 계산하도록
고쳤다. 그러면 같은 값을 여러 곳에서 계산하다 어긋나는 걸 막을 수 있다.

## 아직 남은 것

자세한 건 [`defects.md`](defects.md).

- 정상상태 전진 속도 오차 −4.9 % (`L_w_v` 와 `K_w_f` 균형)
- 스윙 제어에 `J̇q̇` 항이 없음
- MuJoCo 접촉의 연성 침투 약 11 mm
- `(3,1)` 과 `(3,)` 형상이 섞여 있음
- MPC 풀이 시간 미측정 — 30 Hz 와 추가 풀이의 실시간 여유를 아직 모름

### 마찰뿔 대각 미끄러짐 — 아직 확인 못 함

MPC 는 사각뿔 제약이라 대각 방향으로 유효 `μ = √2 · 0.6 = 0.849` 까지 명령할 수
있고, MuJoCo 는 타원뿔이라 0.600 에서 미끄러진다. 그래서 대각 방향 미끄러짐을 예상했다.

`G_gallop` 을 뷰어로 봤을 땐 미끄러지지 않았다. 초기 커밋(`d49ac30`)에는
"galloping 의 경우 마지막 뒷발이 미끄러지면서 보행이 무너짐"이라고 적혀 있어서,
결함 10·11·13 수정 중 하나가 영향을 준 것 같다.

다만 명령된 힘이 애초에 대각 끝까지 안 갔을 수도 있다. 확인하려면 지지 다리마다

    ‖f_xy‖ / (μ · f_z)

를 기록해서 1.0(원뿔 경계)에 얼마나 가까운지 봐야 한다. 이 측정은 아직 안 했다.

### bound / gallop 출발 직후 흔들림

`G_bound`, `G_gallop` 은 출발 직후 크게 흔들리다가 속도가 붙으면 안정된다.
원인은 두 가지로 보인다.

- 속도 지령이 계단이다. `t=0` 부터 `v_des`(1.5~2.0 m/s)를 요구하는데 로봇은 정지 상태다.
- 저속에서는 Raibert 발판이 힙 바로 아래에 놓인다(`v · T_stance / 2 ≈ 0`).
  가속할 발판이 없는 상태에서 체공 구간이 먼저 온다. bound 는 duty 0.4, gallop 은 0.25.

실제 동물은 stand → trot → gallop 으로 넘어가는데, 여기서는 게이트가 `t=0` 부터 고정이다.

해볼 만한 것:

1. 속도 지령 램프 — 가장 간단하다. 참조 궤적만 바꾸면 된다.
2. 게이트 전이 — 전이 시점의 위상 연속성까지 다뤄야 해서 일이 크다.

1 만 먼저 넣어 보면 원인을 나눌 수 있다. 램프로 해결되면 지령 계단이 원인이고,
남으면 게이트 자체가 저속에서 안 맞는 것이다.

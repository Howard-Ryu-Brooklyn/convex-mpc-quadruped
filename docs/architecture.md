# 아키텍처 — 경계가 왜 거기 있는가

파일을 어떻게 나눌지는 아키텍처가 아니다. 아키텍처는 **경계를 어디에 긋는가**이고,
이 저장소의 경계는 네 가지 기준으로 정해졌다.

## 기준 1 — 진리의 종류가 바뀌는 곳

`plants/srb.py` 는 **정확하다.** 13-상태 단일 강체 방정식을 그대로 적분하고,
발 위치를 운동학적으로 강제한다. `plants/mujoco_plant.py` 는 **근사다.**
접촉이 부드럽고, 발이 미끄러지고, 관절에 감쇠와 마찰이 있다.

둘은 다른 질문에 답한다.

- SRB: "내 MPC 가 **이 방정식**에 대해 맞는가" — 외부 변화 없이 알고리즘만
- MuJoCo: "그 방정식이 **실제와 얼마나 다른가**" — 선형화 가정의 강인성

한 클래스에 섞으면 실패했을 때 **어느 쪽이 틀렸는지 알 수 없다.** 그래서
`plants/plant_base.py` 에 인터페이스를 두고 구현을 둘로 나눈다. 러너에서
바뀌는 것은 한 줄뿐이다.

```python
scenario_runner :  robot = SRBDynamics(...)
mujoco_runner   :  robot = MuJoCoPlant(...)
```

두 러너를 합치지 않는 이유도 같다. 공유해야 하는 것은 **제어 로직**이지
실험 진행 방식이 아니다. 질문이 다르면 보고 싶은 진단값도 다르고
(MuJoCo 쪽만 관절 토크·접촉력·yaw unwrap 감시값을 본다),
발산 판정 기준도 다르다(SRB 는 NaN, MuJoCo 는 `|roll| or |pitch| > 60°`).

### 의도한 차이는 선언하고, 나머지는 실패시킨다

두 모델이 다르다는 사실 자체가 이 실험의 내용이므로, 차이를 지우면 안 된다.
대신 `plants/model_audit.py` 가 **의도한 차이 8 개를 선언**하고,
선언되지 않은 차이가 나오면 `UnexpectedModelMismatch` 를 던진다.

| 의도한 차이 | 왜 |
|---|---|
| 마찰: MPC 사각뿔 / MuJoCo `cone="elliptic"` | MPC 제약이 실제 제약의 외부 근사임을 시험하려고 |
| 관절 감쇠·마찰·armature (MuJoCo 에만) | 이상적 모델이 무시한 것의 크기를 재려고 |
| 관성 텐서 (SRB 는 몸통만, MuJoCo 는 합성) | 논문 값을 그대로 쓰기로 한 결정 |

다리 순서, 힙 배치, μ 값, 토크 한계, 액추에이터 수, 발 반지름이 어긋나면
**즉시 실패한다.** 모델이 조용히 바뀌는 것을 막는 장치다.

## 기준 2 — 규약이 바뀌는 곳

단위, 좌표계, 부호, 원점, 각도의 접힘 여부. 경계에는 **주석이 아니라 타입**을 둔다.

이 저장소에서 찾은 결함 13 개 중 6 개가 규약 문제였고, **전부 독스트링에는
정확히 적혀 있었다.** 독스트링은 규약을 강제하지 못한다.

지금 타입이 강제하는 것들:

- `RobotState`, `ControlCommand` 는 frozen 이고 생성 시 형상을 검증한다.
- `ControlCommand` 는 **스윙 다리가 정확히 0 의 힘을 싣는지** 검증한다.
  솔버 잔차 크기의 값도 거부한다.
- `MultiRateClock` 은 `sim_hz % mpc_hz != 0` 을 **생성 시점에** 거부한다.
- `ScenarioSpec` 은 `TypedDict` 라 키 오타가 검사기에 잡힌다.
- `Leg` 는 `IntEnum` 이다. 주석에만 있던 FR/FL/RR/RL 순서를 강제한다.
- `_W` / `_B` 접미사가 프레임을 이름에 박아 넣는다.

## 기준 3 — 주기가 다른 곳

네 개의 주기가 있다.

```
물리 적분 9000 Hz  ──▶  스윙·계획 1000 Hz  ──▶  MPC 30 Hz  ──▶  로깅 30~100 Hz
```

둘이 우연히 같으면 **에일리어싱된 결함이 영원히 안 보인다.** 실제로
`log_hz == mpc_hz` 였던 탓에 33 ms 지연이 로그에서 사라져 있었다.

여기서 나온 두 규칙:

- **이산 사건은 이벤트로 구동한다.** 접촉은 이산 사건이라 고정 주기로 표본화하면
  지연이 반드시 남고, 주기를 올려도 줄어들 뿐 없어지지 않는다. 접촉 상태가 바뀌는
  순간 MPC 를 다시 푼다 — 비용은 정규 90 회에 추가 6 회(+6.7 %)였고, 공중에 뜬
  다리에 힘이 실리던 1,800 스텝이 0 이 됐다.
- **연속량은 계단으로 주지 않는다.** 발판 목표를 MPC 주기로 갱신하면 스윙 중인
  발에 계단 입력이 들어간다(측정 19.7 mm). 계획의 주기는 계획이 정한다.

## 기준 4 — 변하는 축이 다른 곳

```
core  ◀──  control  ◀──  plants  ◀──  experiments  ◀──  viz
```

`core/` 는 로봇이 바뀌어도 안 바뀐다(회전, 각도 unwrap, 시계, 베지에, 기구학).
`control/` 은 제어기가 바뀌면 바뀐다. `plants/` 는 물리 모델이 바뀌면 바뀐다.
`viz/` 에는 아무도 의존하지 않는다.

`core` 는 `control` 을 모르고, `control` 은 `plants` 를 모른다. 러너만이 조립한다.

이 방향은 **실제로 깨져 있었다.** `control/gait_planning.py` 안에 matplotlib 을
import 하는 시각화 함수와 `__main__` 데모가 함께 있었다. 그러면 제어기를 import
하는 것만으로 플로팅 라이브러리가 딸려 온다. 그림은 `viz/gait_plot.py` 로 옮겼고,
지금은 `core`/`control`/`plants`/`experiments` 어디에도 matplotlib 이 없다.

> 의존 방향은 문서에 쓰는 것이 아니라 **확인하는 것**이다.
> `grep -rn matplotlib src/quadruped_mpc/{core,control,plants,experiments}` 가
> 비어 있는지가 이 절의 진위를 정한다.

## 자기 위치를 아는 곳은 하나뿐

`paths.py` 만이 저장소 루트를 계산한다. 예전에는 스크립트마다
`ROOT = Path(__file__).resolve().parent.parent` 를 각자 계산했고, 파일을 한 칸
옮기는 순간 조용히 다른 곳을 가리켰다. **같은 사실을 두 곳에서 계산하면
반드시 갈라진다.**

## 아직 열려 있는 것

정직하게 남긴다. 자세한 것은 [`defects.md`](defects.md).

- 정상상태 전진 속도 오차 −4.9 % (`L_w_v` 와 `K_w_f` 의 균형 문제)
- 스윙 제어에 `J̇q̇` 항이 없다
- MuJoCo 접촉의 연성 침투 약 11 mm
- `(3,1)` 과 `(3,)` 형상이 섞여 있다

### 마찰뿔 대각 미끄러짐 — 재봤으나 관측되지 않음

MPC 는 사각뿔 제약을 쓰므로 대각 방향으로 유효 `μ = √2 · 0.6 = 0.849` 까지
명령할 수 있고, 엔진은 타원뿔이라 0.600 에서 미끄러뜨린다. 그래서 대각
방향에서 미끄러질 것이라고 예측했다.

`G_gallop` 을 뷰어로 보니 **미끄러지지 않는다.** 저장소 초기 커밋(`d49ac30`)에
"galloping 의 경우 마지막 뒷발이 미끄러지면서 보행이 무너짐"이라고 적혀
있으므로, 결함 10(이벤트 구동) · 11(IK 부호) · 13(발판 계획 주기) 중
무엇인가가 이것을 고친 것으로 보인다.

**그러나 이것은 예측을 반증하지 않는다.** 미끄러지지 않았다는 것은
"명령된 힘이 실제로 대각 코너까지 가지 않았다"는 뜻일 수도 있기 때문이다.
제대로 재려면 지지 다리마다

    ‖f_xy‖ / (μ · f_z)

를 기록해서 이 값이 1.0(원뿔 경계)에 얼마나 근접하는지, 그리고 1.0 을
넘는 구간이 있는지 봐야 한다. **그 측정을 아직 하지 않았다.**
"현상이 안 보였다"와 "원인이 없다"는 다르다.

### bound / gallop 의 초기 과도 — 정지 상태에서 체공 게이트를 시작한다

`G_bound`, `G_gallop` 은 출발 직후 몸이 무너지듯 흔들리다가 속도가 붙으면서
거동을 되찾는다. 두 가지가 겹친 것으로 보인다.

- **속도 지령이 계단이다.** 참조 궤적이 `t=0` 부터 `v_des`(1.5~2.0 m/s)를
  요구하는데 로봇은 정지해 있다.
- **저속에서 Raibert 발판이 힙 바로 아래에 놓인다.** 오프셋이
  `v · T_stance / 2` 이므로 `v ≈ 0` 이면 0 에 가깝다. 즉 **가속할 발판이
  없는 상태에서 체공 구간이 먼저 찾아온다.** bound 는 duty 0.4,
  gallop 은 0.25 다.

실제 동물은 정지에서 곧바로 galloping 하지 않는다 — stand → trot → gallop 으로
전이한다. 여기서는 게이트 스케줄이 `t=0` 부터 고정이다.

조치 후보 두 가지. 아직 하지 않았다.

1. **속도 지령 램프** — `v_des` 를 계단이 아니라 유한한 가속도로 올린다.
   가장 싸고, 참조 궤적 생성만 건드린다.
2. **게이트 전이 스케줄** — 속도에 따라 게이트를 바꾼다. 제대로 하려면
   전이 시점의 위상 연속성을 다뤄야 해서 훨씬 크다.

둘 중 무엇이 원인의 더 큰 몫인지는 아직 모른다. 1 만 넣고 재보면
**갈라진다** — 램프만으로 해결되면 원인은 지령의 계단이고, 남으면
게이트 자체가 저속에서 성립하지 않는다는 뜻이다.
